# 운영 환경과 개인정보 보호

이 문서는 서버 구성, 백업과 로그 정리 작업, 접근 권한, 유출 사고 대응과 서버 설정을 다룬다.
개인정보의 수집 항목, 보관 기간, 처리 위탁과 파기는 [개인정보 정책서](../policy/privacy.md)를 따른다.
이 문서의 내용은 서버 저장소의 `docs/`로 옮길 대상이다.

마지막 확인: 2026-11-25, 서버 저장소 구현 기준. 운영 서버와 개발 서버의 설정은 2026-11-16 기준.

## 서버 구성

서버와 파일 저장소는 모두 Oracle Cloud Infrastructure(OCI) 춘천 리전(`ap-chuncheon-1`)에 있다. 서울 리전이 아니다.

| 데이터 | 저장 위치 |
| --- | --- |
| 회원, 여행, 지출, 로그인 세션 | 운영 데이터 서버의 PostgreSQL |
| 운영 DB 백업 | OCI Object Storage 비공개 버킷 |
| 서버 로그 | 개발과 모니터링 서버의 Loki |
| 로그인 기록 | 운영 데이터 서버의 PostgreSQL |
| 서버 지표(CPU, 메모리) | 개발과 모니터링 서버의 Prometheus, 14일 보관 |

운영 데이터 서버는 공인 IP가 없는 사설 서브넷에 있다. PostgreSQL(5432)과 Redis(6379)는 운영 앱 서버에서 오는 연결만 허용한다.

데이터별 보관 기간은 [개인정보 정책서의 저장 위치와 보관 기간](../policy/privacy.md#저장-위치와-보관-기간)을 따른다.

## 백업과 로그 정리

운영 DB는 매일 04:00(KST)에 전체 백업해 OCI Object Storage 비공개 버킷에 올린다. 7일이 지난 백업은 지우되, 최근 성공한 백업 7개는 남긴다. 매월 1일 백업을 별도 환경에 복원해 복구되는지 시험한다.

3개월이 지난 로그인 기록은 서버 스케줄러가 매일 03:30(KST)에 지운다.

## 전송 구간 암호화와 접근 권한

- 앱과 서버 사이의 HTTPS는 지금 임시 도메인 인증서를 쓰며, 실제 도메인이 정해지면 바꾼다.
- 서버에 사람이 접속할 때는 사설 네트워크(Tailscale)를 거쳐 SSH 키로만 로그인한다. 비밀번호 로그인은 막혀 있다.
- 배포는 배포 전용 계정이 허용된 배포 명령만 실행할 수 있다.
- DB와 Redis는 서비스 전용 계정과 비밀번호로 접근하며, 비밀번호는 서버의 환경 파일에만 둔다.

## 유출 사고 때 바로 할 수 있는 차단 조치

| 조치 | 효과 |
| --- | --- |
| JWT 서명 키(`JWT_SECRET`) 교체 후 재배포 | 발급한 모든 Access Token, Refresh Token과 가입 전용 토큰이 무효가 된다. 모든 회원이 다시 로그인한다 |
| 로그인 세션 일괄 종료(`auth_session.revoked_at` 일괄 기록) | 서명 키를 바꾸지 않고 기존 세션만 끊는다 |
| DB, Redis, 외부 API 키 교체 | 유출된 비밀값으로 접근하지 못하게 한다 |
| 서버 접속 계정, SSH 키와 Tailscale 기기 제거 | 사람의 서버 접근을 회수한다 |
| 이전 이미지로 롤백 | 배포 도구로 직전 정상 버전으로 되돌린다 |

유출 규모는 DB에서 영향받은 회원 수와 항목을 SQL로 바로 셀 수 있다.

1차 기술 대응(원인 파악, 접근 차단, 로그 보존)은 BE 담당자 3명이 1차, 2차, 3차 순서로 맡는다. 담당자의 연락처는 이 문서에 적지 않고 유출 대응 매뉴얼에서 관리한다. 예방 점검은 출시 전 1회 하고, 이후 분기마다 1회 한다.

클라우드 사업자에게 보안 사고 지원을 요청할 때는 OCI 콘솔의 도움말(?)에서 Create a Support request를 선택하고 Service Request로 접수한다. 전화는 오라클 한국 고객지원(+82 1588-8501)으로 한다.

회원에게 알리는 방법은 [개인정보 정책서의 보호 조치와 유출 통지](../policy/privacy.md#보호-조치와-유출-통지)를 따른다.

## 서버 설정

| 환경 변수 | 사용하는 곳 |
| --- | --- |
| `JWT_SECRET` | Billit 토큰 서명. 64바이트 이상의 값을 base64로 인코딩해 넣는다. |
| `GOOGLE_CLIENT_ID` | Google ID 토큰의 발급 대상 검증 |
| `KAKAO_NATIVE_APP_KEY` | Kakao ID 토큰의 발급 대상 검증 |
| `APPLE_TEAM_ID`, `APPLE_KEY_ID`, `APPLE_CLIENT_ID`, `APPLE_PRIVATE_KEY_BASE64` | Apple ID 토큰 검증과 인가 코드 교환 |
| `AUTH_TOKEN_ENCRYPTION_KEY` | Apple Refresh Token 암호화 |

개발 서버와 운영 서버에 값을 등록했다. 값은 저장소에 기록하지 않는다.

API 문서 경로(`/swagger-ui.html`, `/api-docs/**`, `/scalar/**`)는 개발 서버에서 게이트웨이의 별도 인증으로 보호하고, 운영 서버에서는 게이트웨이가 막는다.

`JWT_SECRET`은 개발 서버와 운영 서버에 서로 다른 값을 쓰며, 값이 없으면 서버가 시작되지 않는다. `GOOGLE_CLIENT_ID`는 개발 서버에 개발용, 운영 서버에 출시용 웹 클라이언트 ID를 쓴다.

> 논의 필요
>
> Kakao 개발자 콘솔의 OpenID Connect 활성화 여부. Kakao ID 토큰은 이 설정을 켜야 발급된다. BE 담당자가 콘솔에서 확인한다.

## 영수증 인식 경로의 서버 설정

영수증 이미지의 처리 기준은 [지출 설계서의 영수증 이미지 처리](expense.md#영수증-이미지-처리)를, 수탁자와 국외 이전은 [개인정보 정책서의 처리 위탁과 국외 이전](../policy/privacy.md#처리-위탁과-국외-이전)을 따른다.

지금 설정에서는 큰 이미지가 디스크 임시 파일을 거치므로, 영수증 인식 경로에서 다음 설정을 바꾼다.

| 위치 | 지금 동작 | 바꿀 설정 |
| --- | --- | --- |
| Nginx | `client_body_buffer_size`(기본 16KB)보다 큰 요청 본문을 앱에 넘기기 전에 임시 파일(`client_body_temp`)로 쓴다. | 영수증 인식 경로만 `client_body_buffer_size`를 요청 본문 한도(`client_max_body_size`, 지금 15MB)와 같게 올린다. 운영은 진입점 Nginx 한 곳에서 바꾼다. 개발은 요청이 진입점 Nginx를 거쳐 개발 게이트웨이 Nginx로 한 번 더 넘어가므로 두 곳 모두에서 바꾼다. |
| Spring | multipart의 `file-size-threshold`가 기본값 0이라 업로드 파일을 Tomcat 임시 디렉터리에 파일로 받는다. | `file-size-threshold`를 요청 본문 한도 이상으로 올린다. |

Nginx 설정은 Infra 저장소에서, Spring 설정과 확인 테스트는 영수증 인식 구현 PR에서 반영한다.

이미지가 디스크를 거치지 않는지는 다음 두 가지로 확인한다. Spring과 Nginx 모두 요청이 끝나면 임시 파일을 지우므로, 요청이 끝난 뒤 임시 디렉터리가 비어 있는지만 봐서는 확인할 수 없다.

- 영수증 인식 구현 PR에 실제 이미지를 업로드하고, 요청을 처리하는 도중에 Tomcat 임시 디렉터리에 파일이 생기지 않는지 검사하는 테스트를 둔다. 이 테스트가 기존 설정(`file-size-threshold` 0)에서는 실패하는지 먼저 확인한다.
- dev 배포 후 영수증 이미지를 업로드하고, 진입점 Nginx와 개발 게이트웨이 Nginx의 error log에 `a client request body is buffered to a temporary file` 경고가 없는지 Grafana에서 확인한다.

> 논의 필요
>
> 동시에 처리할 영수증 인식 요청의 최대 수를 구현할 때 정한다.
> 운영 앱 컨테이너의 메모리 한도(2GB) 안에서 정한다.
> 요청 하나가 쓰는 메모리는 Gemini inline 전송의 base64 인코딩(약 1.33배)과 처리 중 복사본을 고려해 원본 크기의 2~3배로 잡는다.
>
> 운영 진입점 Nginx와 개발 게이트웨이 Nginx는 컨테이너 메모리 한도가 128MB여서, 버퍼를 15MB로 올리면 업로드 8개 정도를 동시에 받을 때 Nginx 메모리가 먼저 찬다.
> Nginx는 요청 본문을 모두 받은 뒤 앱으로 넘기므로 앱의 동시 요청 제한만으로는 막지 못한다.
> 동시 요청 수를 정할 때 Nginx 메모리 한도를 올릴지, 영수증 인식 경로에 `limit_conn`을 걸지 함께 정한다.
>
> 15MB는 Nginx가 모든 요청에 적용하는 본문 한도이며, 영수증 이미지의 용량 상한은 [영수증 인식 API](../api-spec/expense.md#exp-09-영수증-인식)에서 아직 정하지 않았다.
> 상한이 정해지면 Nginx 버퍼, Spring 기준값과 동시 요청 수를 그 값에 맞춰 다시 정한다.
