# 생성 요청 멱등성

관련 정책: [지출 입력과 저장](../policy/expense.md#입력과-저장)

## 회의 결정

앱에서 고유키를 생성해 지출 저장 요청에 함께 보낸다. 서버는 같은 키의 재요청으로 지출을 다시 저장하지 않는다. DB 커밋 후 응답을 받지 못해 재시도하더라도 같은 지출이 두 건 생기면 안 된다.

이 절의 회의 결정은 지출 생성 요청에 대한 것이다. 여행 생성은 아래 별도 결정에 따라 적용한다. 수정과 정산 확정까지 같은 키 체계를 적용하는 것은 별도 검토 대상이다. 잠금 토큰과 저장 요청의 고유키는 목적과 생애주기가 다르므로 혼용하지 않는다.

### 예시: 저장됐지만 앱이 응답을 받지 못한 경우

민지가 숙소비 저장 버튼을 눌렀다. 앱은 고유키 `save-A`를 보냈고 서버는 지출 501 저장을 완료했지만, 네트워크가 끊겨 앱에는 성공 응답이 도착하지 않았다. 키 이름과 지출 번호는 설명용이다.

| 순서 | 앱의 행동 | 서버가 보장할 결과 |
| --- | --- | --- |
| 1 | `save-A`로 숙소비를 저장한다. | 지출 501을 한 번 저장한다. |
| 2 | 성공 여부를 몰라 같은 저장을 `save-A`로 재시도한다. | 기존 성공 요청임을 식별하고 새 지출을 만들지 않는다. |

응답 방식과 관계없이 숙소비는 한 건만 저장돼야 한다. 같은 저장의 재시도는 같은 키를 사용해야 서버가 원래 요청을 식별할 수 있다.

> 논의 필요
>
> 기존 지출 결과 반환 vs 중복 처리 안내, FE에서 동일 저장 키를 생성하고 유지하는 시점

## 저장 구조 제안

현재 검토 DDL에는 고유키 컬럼이나 멱등성 기록 테이블이 없다.

> 구현 제안
>
> 아래 두 저장 구조를 비교한다. 컬럼 후보와 타입은 각 안의 가정이다.

| 방식 | 필요한 데이터 | 영향 |
| --- | --- | --- |
| `expense`에 보관 | `idempotency_key`, 기존 기록자 ID, 필요하면 요청 내용 식별값 | 지출과 같은 트랜잭션으로 저장하기 쉽다. 실패 이력, 삭제 후 재시도와 보존 기간은 별도 처리가 필요하다. |
| 별도 요청 기록에 보관 | 요청자, 키, 작업 종류, 요청 내용 식별값, 결과 지출 ID, 처리 상태와 필요한 시각 | 업무 데이터와 분리해 관리할 수 있다. 요청 기록과 지출의 원자성, 진행 중 중복 요청 처리가 추가로 필요하다. |

> 논의 필요
>
> expense에 키 보관 vs 별도 요청 기록 테이블

### expense에 보관하는 경우의 컬럼 후보

| 컬럼 | 타입 후보 | 역할 | 확정 여부 |
| --- | --- | --- | --- |
| `idempotency_key` | `UUID` 또는 길이를 제한한 문자열 | 앱이 만든 저장 요청 식별키 | 키 도입 결정, 이름과 타입 후보 |
| `created_by_trip_member_id` | 기존 `BIGINT` | 요청 소유자를 검증하는 기존 기록자 정보 | 기존 검토안 |
| `request_hash` | 해시를 저장할 문자열 또는 바이트 타입 | 같은 키에 다른 내용이 온 경우 비교 | 추가 후보 |

> 논의 필요
>
> 키 타입은 UUID vs 길이를 제한한 문자열
>
> 기록자와 키의 복합 UNIQUE vs 키 단독 UNIQUE, request_hash 도입 및 입력 정규화 기준

## 처리 흐름에서 보장할 것

```text
요청 인증과 권한 검증
→ 고유키와 요청 소유자 확인
→ 처음 처리하는 요청이면 지출과 고유키를 원자적으로 저장
→ 이미 성공한 키면 지출을 추가 생성하지 않음
```

사전 조회 후 저장만으로는 동시 요청을 막을 수 없다. 지출, 품목과 부담액의 저장이 롤백되면 키만 성공 처리로 남지 않아야 한다.

> 구현 제안
>
> 선택한 키 범위에 DB UNIQUE를 두어 동시 요청의 중복 저장을 막는다.

UNIQUE 충돌이 발생한 트랜잭션 안에서 그대로 결과를 조회할 수 있다고 가정하지 않는다. 충돌 처리 후 기존 결과 조회를 어떤 트랜잭션에서 수행할지 선택한 JPA 및 PostgreSQL 구현에 맞춰 검증한다. 다른 제약 위반을 고유키 중복으로 처리하지 않는다.

### 예시: 같은 키의 요청이 동시에 도착하는 경우

DB UNIQUE를 사용하는 제안안을 가정한다. 요청 A와 B가 같은 키로 동시에 도착하면 둘 다 사전 조회에서 ‘저장 기록 없음’을 볼 수 있다.

이후 A가 키와 지출을 먼저 커밋하면 B는 같은 키의 저장을 완료할 수 없어야 한다. 조회 결과만 믿으면 두 지출이 생길 수 있기 때문에 DB에서도 중복을 막는 것이다. 반대로 A가 전체 롤백됐다면 키만 성공한 것으로 남아 이후 재시도를 계속 막아서는 안 된다.

### 예시: 같은 키로 금액까지 바꿔 보낸 경우

첫 요청은 `save-A`, 30,000원이고 재요청은 `save-A`, 35,000원인 상황이다. 같은 키지만 입력 금액은 다르다.

> 구현 제안
>
> request_hash로 같은 키의 요청 내용 차이를 비교한다.

> 논의 필요
>
> 동일 키의 다른 내용 거절 여부, 비교할 입력과 응답 계약

## 논의 필요

> 논의 필요
>
> | 안건 | 선택할 내용 |
> | --- | --- |
> | 저장 위치 | `expense` 컬럼 vs 별도 요청 기록 |
> | 키 범위 | 서비스 전체 vs 요청자 및 작업 종류별 |
> | FE 키 유지 | 같은 저장의 재시도에는 키 유지, 새로운 지출 입력에는 새 키를 발급하는 시점 |
> | 동일 키와 다른 내용 | 거절 여부, 비교할 입력과 정규화 방식 |
> | 재요청 응답 | 기존 지출 결과 반환 vs 중복 처리 결과 안내 |
> | 실패와 진행 중 요청 | 재시도 허용 시점, 대기 또는 거절 방식 |
> | 보존 기간 | 키 만료 여부, 지출 삭제 후 재요청과 키 재사용 |

실제 DB 검증에서는 동일 키 동시 요청으로 지출 한 건만 저장되는지, 커밋 후 응답 유실 재시도, 전체 롤백 뒤 재시도, 다른 요청자의 키 사용과 다른 내용의 동일 키 요청을 확인한다.

## 여행 생성 멱등성

앱은 여행 생성 요청의 `Idempotency-Key` 헤더에 UUID 형식의 고유키를 보낸다. 생성 시도마다 새 키를 만들고, 응답을 받지 못해 같은 요청을 다시 보낼 때만 같은 키를 사용한다. 서버는 같은 회원이 같은 키로 다시 보낸 요청에 여행과 생성자 참여 정보를 다시 만들지 않고 처음 만든 여행을 반환한다. 2026-11-06 API 스펙 검토에서 채택한 방향에 이어 키의 범위와 재응답 방식을 확정했다. 지출 생성의 재응답 방식까지 확정한 것은 아니다.

| 상황 | 서버의 처리 |
| --- | --- |
| 키가 없거나 UUID 형식이 아님 | `400`으로 거절한다. |
| 요청 본문이 유효하지 않음 | 이미 사용한 키여도 고유키를 조회하지 않고 `400`으로 거절한다. |
| 같은 회원이 같은 키와 유효한 본문으로 다시 요청 | 처음과 같이 `201 Created`와 `Location`을 반환하고, `data`에는 처음 만든 여행의 현재 정보를 담는다. |
| 같은 회원이 같은 키로 유효한 본문의 값을 바꿔 요청 | 처음 요청의 본문과 비교하지 않고 처음 만든 여행을 반환한다. |
| 다른 회원이 이미 사용한 키 | 기존 여행 정보를 반환하지 않고 `409 TRIP_IDEMPOTENCY_KEY_REUSED`로 거절한다. |
| 그 키로 만든 여행이 삭제됨 | `409 TRIP_IDEMPOTENCY_KEY_REUSED`로 거절한다. |
| 같은 키의 요청이 동시에 도착 | 여행은 하나만 만든다. 늦게 처리된 요청에는 먼저 만든 여행을 다시 조회해 재요청과 같이 응답한다. |

고유키는 여행 생성에만 사용하며, 키 하나로는 여행 하나만 만든다.
키는 만료 없이 만든 여행과 함께 보관한다.
서버는 요청자 인증과 요청 본문 검증(필수값, 형식과 범위, 여행 기간 순서, `countryCode`와 `customCountryName`의 조합)을 고유키 조회보다 먼저 실행한다.
따라서 본문이 유효하지 않은 요청은 이미 성공한 고유키로 보낸 재요청이어도 고유키를 조회하지 않고 `400`으로 거절한다.
앱이 생성 시도마다 새 키를 만들기 때문에, 본문 검증을 통과하고 같은 키로 온 요청은 응답을 받지 못한 같은 생성 요청의 재시도로 보고 처음 요청의 본문과 비교하지 않는다.

고유키로 기존 결과를 찾을 때도 요청자 인증을 검사하고, 키를 사용한 회원과 요청한 회원이 같은지 확인한다.
여행, 생성자 참여 정보와 고유키는 전체 성공 또는 전체 실패를 보장해야 한다.

여행 행에 `idempotency_key UUID`를 저장하고 키 단독 UNIQUE 제약을 둔다. 고유키는 여행과 같은 트랜잭션에 저장해 함께 성공하거나 실패하며, 같은 키의 요청이 동시에 와도 DB에서 두 번째 저장을 막는다([ERD 변경 목록](erd-changes.md#반영할-변경)).

키를 사용한 회원은 그 키로 만든 여행의 `trip_member` 중 `role = ADMIN`인 행의 `member_id`로 확인하며, `trip`에는 생성자 컬럼을 추가하지 않는다.
생성자 확인은 같은 키로 재요청이 왔을 때만 필요하므로, `trip`을 조회할 때 `ADMIN` 행을 한 번 조인해도 조회 비용은 거의 늘지 않는다.
생성자를 `trip`에도 저장하면 생성자와 관리자를 두 곳에서 관리하게 되고, 관리자를 넘기는 기능이 생기면 어느 쪽을 기준으로 할지 다시 정해야 한다.

같은 키의 요청 두 개가 동시에 오면 늦게 처리된 요청은 고유키 UNIQUE 제약(`uq_trip_idempotency_key`) 위반으로 저장에 실패한다.
PostgreSQL은 오류가 난 트랜잭션에서 더 이상 조회할 수 없으므로, 여행 생성 처리 전체를 하나의 트랜잭션으로 묶지 않는다.
여행, 생성자 참여 정보와 고유키의 저장만 한 트랜잭션으로 묶는다.
고유키 중복으로 저장에 실패하면 그 트랜잭션을 롤백한 뒤 새 트랜잭션에서 고유키로 여행을 다시 조회한다.

다시 조회한 여행이 같은 회원이 만든 여행이면 `201 Created`와 `Location`을 반환하고, `data`에는 먼저 만든 여행의 현재 정보를 담는다.
다른 회원이 만든 여행이거나 삭제된 여행이면 `409 TRIP_IDEMPOTENCY_KEY_REUSED`로 거절한다.
다시 조회했을 때 여행 행이 없어도 삭제된 여행과 같이 `409 TRIP_IDEMPOTENCY_KEY_REUSED`로 거절한다.

저장 실패의 SQLSTATE가 `23505`(UNIQUE 위반)이고 위반한 제약 이름이 `uq_trip_idempotency_key`일 때만 고유키 중복으로 보고 여행을 다시 조회한다.
다른 제약 위반은 고유키 중복으로 처리하지 않는다.

구현 시 동일 키 동시 요청과 응답 유실 후 재시도에서 여행 및 생성자 참여 정보가 한 번만 생성되는지 확인한다. 일부 저장 실패 시 전체 롤백, 다른 회원의 키 사용, 삭제한 여행의 키 재사용과 같은 키의 다른 본문도 함께 검증한다.
