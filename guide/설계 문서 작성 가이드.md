# 설계 문서 작성 가이드

## 목적과 적용 범위

이 가이드는 `design/`에 설계서를 쓰는 기준이다. 근거와 상태는 [공통 문서 작성 가이드](<공통 문서 작성 가이드.md>)를, 문장은 [한국어 표현 가이드](<한국어 표현 가이드.md>)를 따른다.

설계서는 정책서의 업무 규칙을 구현하는 데이터, 쿼리, 트랜잭션과 처리 흐름을 정한다. 설계서에는 팀이 정한 구조를 구현 여부와 관계없이 쓴다. 구현 진행 상황은 서버 저장소의 Issue와 PR에서 관리한다.

## 설계서에 쓰는 내용

설계서에는 현재 정한 구조만 쓴다. 다른 내용은 다음 표의 위치에서 관리하고 설계서에서 링크한다.

| 내용 | 관리하는 위치 |
| --- | --- |
| 데이터, 쿼리, 트랜잭션, 처리 흐름과 실패 처리 | 설계서 |
| 업무 조건과 사용자가 관찰하는 결과 | 정책서 |
| 요청, 응답, 상태 코드와 필드 계약 | API 스펙 |
| 결정의 배경, 검토한 선택지와 이유 | 문서 저장소 논의 Issue의 `논의 결과` |
| 검토 중인 구조와 컬럼 후보 | 논의 Issue, 설계를 제안하는 PR |
| 구현 진행 상황과 구현 PR | 서버 저장소의 Issue와 PR |
| 서버 설정, 배포와 운영 절차 | 서버 저장소의 `docs/` |

다음 섹션은 설계서에 쓰지 않는다. 표의 내용은 오른쪽 위치로 옮긴다.

| 쓰지 않는 섹션 | 옮기는 위치 |
| --- | --- |
| 회의 결정, 설계 결정, 결정한 방향 | 결정이 적용되는 절의 본문 한 문장과 [근거 링크](#결정의-이유) |
| 구현 상태, 구현 PR 목록 | 서버 저장소의 Issue와 PR |
| 변경 이력, 변경 목록 | 문서 저장소의 PR |
| 제안, 후보, 구현 제안 | 논의 Issue, 설계를 제안하는 PR |
| 구현 시 검증, 구현 전 결정 | [검증](#검증) 섹션의 요구사항 문장, 논의 Issue |

## 설계서 단위

- 설계서는 정책서와 같은 업무 영역마다 하나씩 두고, 파일 이름을 정책서와 같게 쓴다.
- 제목은 `[업무 영역] 설계서`로 쓴다.
- 업무 영역 안의 하위 시스템은 설계서 안의 `##` 절로 나눈다.
- 하위 시스템 절에 `####`가 필요하면 그 하위 시스템을 `<업무 영역>-<하위 시스템>.md`로 나누고, 업무 영역 설계서에는 개요와 링크를 남긴다.
- 테이블은 한 설계서의 `저장 데이터`에서만 정의한다.
- 설계서가 없는 업무 영역에 설계가 생기면 설계서를 만들고, [설계서 목록](../design/README.md)에 문서 이름과 범위를 추가한다.

## 여러 업무 영역에 걸친 설계

- 한 업무 영역이 다른 업무 영역의 데이터나 상태를 전제로 동작하면, 전제로 하는 쪽 설계서에 설계를 쓴다.
- 다른 설계서에는 그 설계가 영향을 주는 위치에 한 문장과 링크를 쓴다.

## 문서 구조

다음 순서로 쓴다. 내용이 없는 섹션은 쓰지 않는다.

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 개요 | 설계서의 범위와 관련 정책서 | 문단, 3문장 이하 |
| 저장 데이터 | 테이블, 컬럼, 제약과 키 | 표 |
| 처리 흐름 | 요청부터 응답까지의 순서 | 순서 다이어그램과 문장 목록 |
| 쿼리 | 핵심 조회와 갱신 쿼리 | `sql` 블록 |
| 트랜잭션과 동시성 | 트랜잭션 범위, 잠금과 충돌 처리 | 요구사항 문장 목록 |
| 실패 처리 | 실패 조건과 결과 | 요구사항 문장 목록 |
| 검증 | 테스트로 확인할 조건 | 요구사항 문장 목록 |

하위 시스템이 둘 이상이면 하위 시스템마다 `##` 절을 두고, 그 안에서 `###`로 위 순서를 따른다. `####`가 필요하면 [설계서 단위](#설계서-단위)에 따라 설계서를 나눈다.

```markdown
# 환율 설계서

## 개요

## 저장 데이터

## 처리 흐름

## 트랜잭션과 동시성

## 실패 처리

## 검증
```

### 개요

- 설계서가 다루는 범위와 다루지 않는 범위를 쓴다.
- 관련 정책서의 절을 링크한다. 정책서의 업무 규칙을 설계서에 다시 쓰지 않는다.

### 저장 데이터

- 표의 열은 이름, 타입, 제약, 뜻 순서로 쓴다.
- NULL을 허용하는 컬럼은 `뜻`에 NULL의 의미를 쓴다.
- 정하지 않은 컬럼은 표에 쓰지 않는다. 논의 Issue에서 정한 뒤 표에 추가한다.

```markdown
| 이름 | 타입 | 제약 | 뜻 |
| --- | --- | --- | --- |
| `expense.paid_date` | `DATE` | NOT NULL | 회원이 입력한 결제 당시의 현지 날짜 |
```

### 처리 흐름

- 요청부터 응답까지의 순서는 [순서 다이어그램](<예시 블록 가이드.md#순서-다이어그램>)으로 쓴다.
- 다이어그램 아래에는 다이어그램이 보여 주지 않는 조건만 문장 목록으로 쓴다.
- 다이어그램의 조건과 롤백 범위는 쿼리와 트랜잭션 섹션의 내용과 같게 쓴다.

### 쿼리

- 쿼리 블록 앞에는 쿼리가 하는 일을 한 문장으로 쓴다.
- 파라미터, 권한을 확인하는 위치와 쿼리가 속한 트랜잭션을 쓴다.

### 트랜잭션과 동시성, 실패 처리

- 문장은 [요구사항 문장 가이드](<요구사항 문장 가이드.md>)의 문장 틀로 쓴다.
- 서버는 커밋한 뒤에 성공 응답을 보낸다. 커밋 전에 응답하는 흐름이 있으면 그 조건을 쓴다.
- 조건부 갱신이 0건인 결과와 SQL 오류를 나누어 쓴다.

### 검증

- 검증에는 테스트로 확인할 조건을 요구사항 문장으로 쓴다. `-하는지 확인한다`로 쓰지 않고, 통과했을 때의 동작을 쓴다.
- 테스트 실행 결과는 설계서에 쓰지 않고 PR의 `검증 결과`에 쓴다.

```diff
# 검증 문장의 형식 (가상 예시)
- 가입 전용 토큰으로 일반 회원 API를 요청하면 거절되는지 확인한다.
+ 가입 전용 토큰으로 일반 회원 API를 요청하면 서버는 `401`로 거절한다.
```

## 결정의 이유

결정의 이유는 그 결정이 적용되는 위치에 한 문장으로 쓰고, 결정을 기록한 논의 Issue의 `논의 결과`나 제안 PR 하나를 링크한다. 회의 날짜, 참석자와 논의 경과는 쓰지 않는다. 다음은 가상 예시다.

```markdown
지출 수정 잠금은 DB 행 잠금을 쓴다. 근거: [Issue #21 논의 결과](https://github.com/JECT-Study/Billit-5th-Docs/issues/21)
```

외부 논의의 출처 표기는 [문서 기여 규칙](../CONTRIBUTING.md#외부-논의와-결정)을 따른다. 자료가 충돌하면 변경 경위와 적용 범위를 확인하고, 폐기한 해석은 설계서에 남기지 않는다.

## 정하지 않은 내용

- 정하지 않은 내용은 설계서에 쓰지 않고 [공통 문서 작성 가이드](<공통 문서 작성 가이드.md#미결정-사항>)에 따라 논의 Issue로 관리한다.
- 설계서에는 채택한 구조와 처리만 쓴다. 검토 중인 구현 방식과 컬럼 후보는 논의 Issue나 설계를 제안하는 PR에서 다룬다.

## 예시

- 예시는 [예시 블록 가이드](<예시 블록 가이드.md#확정형>)의 확정형으로 쓴다.
- 인물, ID와 시각은 블록 앞 문장에 가상 예시라고 밝힌다.
- 정하지 않은 내용에 따라 결과가 달라지면 결론을 고르지 않고, 같은 입력에서 무엇이 달라지는지 보여 준다.

## 적용 시점

이 가이드는 새로 만드는 설계서와 새로 수정하는 절에 적용한다. 수정하지 않는 절은 기존 내용을 유지한다.

- 설계서를 나누거나 합치는 작업은 절을 수정하는 PR과 별도 PR로 한다. 이 PR에서는 문장을 고치지 않고 옮기기만 한다.
- 여러 설계서를 이 가이드에 맞추는 작업은 한 PR로 할 수 있다. 이때 커밋은 설계서마다 나눈다.

## 완료 전 확인

다음 항목은 새로 만든 설계서와 이번 PR에서 수정한 절에 적용한다.

- 설계서에 구현 진행 상황, 회의 경과와 변경 이력이 없는가?
- 섹션이 정한 순서를 따르는가?
- 여러 업무 영역에 걸친 설계를 한 설계서에만 쓰고 다른 설계서에서 링크했는가?
- 테이블을 한 설계서에서만 정의했는가?
- 정책서의 업무 규칙을 다시 쓰지 않고 링크했는가?
- 결정의 이유가 한 문장이고 논의 Issue나 PR을 링크했는가?
- 트랜잭션, 실패 처리와 검증이 요구사항 문장인가?
- 다이어그램, 쿼리와 본문의 조건이 같은가?
