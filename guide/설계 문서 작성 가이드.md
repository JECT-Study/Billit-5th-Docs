# 구현 설계 작성 가이드

## 문서의 역할

정책서는 업무 조건과 결과를, 설계서는 이를 구현하는 데이터, 쿼리와 트랜잭션을 정의한다. 업무 규칙은 정책서를 링크하고, 같은 내용을 반복해서 정의하지 않는다.

각 문서는 결정한 동작을 먼저 쓰고 저장 데이터, 처리 순서와 실패 결과를 이어서 설명한다. 필요한 위치에 시나리오와 SQL, 시퀀스 다이어그램을 배치한다.

## 상태 표시

| 상태 | 작성 방식 |
| --- | --- |
| 확정 설계 | 본문에 조건과 동작을 서술한다. |
| 기존 검토안 | 기존 ERD 또는 흐름 문서에서 가져온 구조임을 표시한다. 구현 완료와 구분한다. |
| 구현 제안 | 해당 영역 앞에 `> 구현 제안`을 두고 적용 범위를 명시한다. 컬럼명과 타입, 쿼리의 가정을 포함한다. |
| 논의 필요 | 해당 영역 아래 `> 논의 필요` 블록에 선택지와 확인할 조건을 모은다. |
| 추후 검토 | 현재 범위 밖의 검토 항목을 `> 추후 검토`로 표시한다. |

본문에 ‘아직 미결이다’, ‘나중에 정한다’는 설명을 반복하지 않는다. 확정된 부분은 본문에 남기고, 남은 선택만 상태 블록으로 옮긴다.

```markdown
적용 환율은 지출에 복사해 저장한다. 저장 환율을 수정해도 기존 지출은 바꾸지 않는다.

> 구현 제안
>
> API 출처와 기준일을 지출에 함께 복사하는 아래 컬럼 구성을 검토한다.

> 논의 필요
>
> 출처 컬럼은 문자열 코드 vs enum
```

이미 결론 난 항목은 상태 블록에서 제거하고 본문에 통합한다. 권장 의견은 채택 결정과 구분하며, 답변의 범위를 넘어 새 정책을 확정하지 않는다.

## 컬럼과 제약

기존 컬럼, 변경할 컬럼과 추가 후보를 구분한다. 테이블명, 타입, NULL의 의미와 제약을 함께 설명한다. 제안 컬럼은 표 제목이나 상태 블록으로 후보임을 표시하고, 셀마다 ‘미정’을 반복하지 않는다.

DB 변경이 필요하면 현재 검토 DDL과의 차이를 [ERD 변경 목록](../design/erd-changes.md)에 모은다. 문서의 제안을 실제 적용된 스키마처럼 표현하지 않는다.

## 시나리오와 쿼리

시나리오는 입력 또는 요청, 처리 순서, 저장 전후와 실패 결과를 보여준다. 인물, ID와 시각은 설명용임을 밝힌다. 가정한 계산 단위와 선택안은 예시 앞에 표시한다.

SQL은 파라미터, 권한 검증 위치와 트랜잭션 범위를 설명한다. 성공 응답은 커밋 후에 보내며, 조건부 갱신 0건과 SQL 오류를 구분한다. Mermaid 시퀀스는 본문과 SQL의 조건 및 롤백 범위와 일치시킨다.

미결 정책에 따라 결과가 달라지는 예시는 결론을 임의로 고르지 않고, 같은 입력에서 무엇이 달라지는지 보여준다.

## 근거와 검증

관련 정책을 문서 앞에 연결하고, 설계의 근거가 된 결정과 검토 자료를 구분한다. 외부 논의의 출처는 [문서 기여 규칙](../CONTRIBUTING.md#외부-논의와-결정)을 따른다. 자료가 충돌하면 변경 경위와 적용 범위를 확인하고, 폐기된 해석은 현재 설계에 남기지 않는다.

검증 항목은 실행할 검증과 실제 실행 결과를 구분한다. 문서 링크 검사나 SQL 조건의 정적 확인을 실제 DB 또는 동시성 검증으로 표현하지 않는다.
