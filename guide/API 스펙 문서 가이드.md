# API 스펙 문서 가이드

## 목적과 적용 범위

이 가이드는 `api-spec/`의 Markdown 문서에 요청과 응답 계약, 검토안을 작성하는 기준이다. 근거와 상태, 설명 흐름은 [공통 문서 작성 가이드](<공통 문서 작성 가이드.md>)를, 문장은 [한국어 표현 가이드](<한국어 표현 가이드.md>)를 따른다.

HTTP 상태, 공통 응답, 인증과 데이터 표현은 [Billit API 공통 규칙](https://github.com/JECT-Study/Billit-5th-Server/blob/develop/docs/contributing/api-conventions.md)을 따른다. [공통 API 스펙](../api-spec/common.md)은 이 기준을 문서에서 참조하기 위한 설명이다. 서로 충돌하면 차이와 영향 범위를 확인하고, 임의로 새로운 규칙을 선택하지 않는다.

## 계약 원본과 문서의 역할

확정된 실행 가능한 계약의 원본은 백엔드의 OpenAPI YAML이다. 관리와 구현 동기화는 [백엔드 API 문서 기준](https://github.com/JECT-Study/Billit-5th-Server/blob/develop/docs/contributing/api-documentation.md)을 따른다.

- Markdown에는 API 범위, 검토할 계약과 클라이언트가 이해해야 하는 설명을 작성한다. 확정된 내용은 대응하는 OpenAPI 경로나 `operationId`를 연결한다.
- 정책이 확정돼도 경로, 필드와 오류 매핑까지 확정된 것은 아니다. 정하지 않은 선택은 본문에 상태를 표시하지 않고 [미결정 사항](<공통 문서 작성 가이드.md#미결정-사항>)에 따라 논의 Issue로 관리한다.
- 합의하지 않은 경로, 필드, 기본값과 오류 코드를 빈칸을 채우기 위해 만들지 않는다. 제안할 때는 적용 범위와 가정을 명시한다.
- 계약을 확정하거나 변경하면 OpenAPI 반영 대상과 관련 PR을 연결한다. 문서 합의를 구현 완료나 배포 완료로 표현하지 않는다.
- 권한과 계산 등 업무 규칙 전체는 정책서를, 저장 구조와 내부 처리 방식은 설계서를 링크한다. 이 문서에는 요청과 응답 처리에 필요한 조건만 설명한다.

## 문서 구조

제목은 `[업무 영역] API 스펙`으로 작성하고, 검토 단계이면 `초안`과 대상 범위를 표시한다. 문서 앞부분에는 목차, 문서 범위와 API 목록을 둔다. 개별 API는 Controller나 화면이 아니라 같은 자원과 목적을 공유하는 업무 영역으로 묶는다.

```markdown
# [업무 영역] API 스펙

## 목차

- [문서 범위](#문서-범위)
- [API 목록](#api-목록)
- [공통 모델](#공통-모델)
- [오류 코드](#오류-코드)

## 문서 범위

## API 목록

## [업무 영역] API

### [API 식별자] [API 이름]

## 공통 모델

## 오류 코드
```

목차에는 실제 업무 영역과 개별 API, 공통 모델도 연결한다. 위 형식의 대괄호 항목은 구조를 설명하기 위한 자리표시자이며 그대로 문서에 남기지 않는다. 공통 모델이나 도메인 오류가 없으면 해당 절은 생략한다.

문서 범위에는 다루는 기능과 제외 범위, 관련 정책과 설계, 계약의 검토 상태를 작성한다. API 목록에는 기능, Method, Path와 인증 조건을 표시한다. 기능 이름은 본문으로 연결하고, 목록과 본문의 경로와 상태를 일치시킨다. API 식별자와 Figma 화면 식별자를 혼용하지 않는다.

## 개별 API 작성 순서

각 API는 다음 순서로 작성한다. 해당하지 않는 항목은 없다는 사실을 짧게 밝히고, 설명할 내용이 없는 하위 표는 생략한다.

1. API 이름 바로 아래에 Method와 Path를 함께 백틱으로 표시한다. Query Parameter는 경로에 붙이지 않고 요청에서 정의한다.
2. 인증에는 필요한 인증 수단과 요청 대상에 대한 권한을 작성한다. 토큰 유무와 여행 참여 여부 같은 업무 권한은 구분한다.
3. 설명에는 호출 목적과 결과를 한두 문장으로 작성한다.
4. 요청에는 입력 위치별 필드와 예시를 작성한다.
5. 성공 응답에는 HTTP 상태, 필요한 헤더, 응답 모델과 예시를 작성한다.
6. 오류에는 실제 발생할 수 있는 조건과 응답을 작성한다.
7. 처리 규칙에는 표만으로 설명하기 어려운 재시도, 충돌과 연관 작업을 작성한다.

둘지 정하지 않은 API는 API 스펙에 쓰지 않고 논의 Issue에서 초안을 다룬다.
구현하기로 한 API는 정한 계약을 본문에 쓰고, 일부 필드나 응답의 남은 선택은 논의 Issue로 관리한다.
본문에는 `제안`, `후보`, `조건부`처럼 API의 확정 여부를 알리는 표시를 쓰지 않는다.

## 요청 작성

요청은 Path Parameter, Query Parameter, Header, Body, Part 순서로 구분한다. 필드 표는 다음 열을 사용한다.

| 필드 | 타입 | 필수 | 기본값 | 규칙 |
| --- | --- | --- | --- | --- |
| `[필드명]` | [전송 타입] | 필수, 선택 또는 조건부 | [기본값 또는 없음] | [허용 값, 범위, null 허용 여부와 조건] |

- 필수 여부는 필드를 보내야 하는지를 뜻한다. `선택`이라고 해서 `null`도 허용하는 것은 아니다.
- 조건부 필드는 필요한 조건과 다른 조건에서의 생략 또는 거절 여부를 설명한다. PATCH는 필드 생략과 `null`의 의미를 구분한다.
- 기본값이 없으면 `없음`으로 표시한다. 값 생략의 의미가 미결이면 임의의 기본값을 넣지 않고 논의 Issue로 관리한다.
- 문자열 길이, 수치 범위, 배열 크기와 허용 값 등 클라이언트가 알아야 할 제약을 작성한다. 미결인 상한을 임의로 정하지 않는다.
- 객체와 배열은 하위 모델로 연결한다. 모델의 필드를 여러 API에 반복해서 정의하지 않는다.
- multipart 요청은 Part별 이름, Content-Type, 필수 여부와 규칙을 먼저 정의한다. JSON Part의 내부 필드는 별도 모델로 설명한다.

## 성공 응답과 모델

성공 응답에는 HTTP 상태와 본문 유무를 먼저 작성한다. 공통 응답의 `data` 안에 들어가는 모델과 응답 전체 구조를 구분하고, `Location` 등 클라이언트가 사용할 헤더도 설명한다.

| 필드 | 타입 | nullable | 포함 조건 | 설명 |
| --- | --- | --- | --- | --- |
| `[필드명]` | [전송 타입 또는 모델 링크] | 예 또는 아니요 | 항상 또는 구체적인 조건 | [값의 의미와 제약] |

- `nullable`은 필드 값이 `null`일 수 있는지, 포함 조건은 필드가 응답에 존재하는지를 뜻한다. 필드 생략, `null`, 빈 문자열과 빈 배열을 같은 의미로 사용하지 않는다.
- 공통 응답을 매번 다시 정의하지 않는다. 개별 API에는 `data`의 구체적인 모델, 페이지 적용 여부와 추가 조건을 작성한다.
- 두 API 이상이 같은 모델을 사용하면 공통 모델로 분리한다. `앞의 응답과 같다` 대신 모델과 필요한 절을 링크한다.
- 목록은 페이지 적용 여부, 필터, 기본 정렬과 동률 처리, 빈 결과와 마지막 페이지 초과 시 응답을 설명한다. 페이지네이션의 공통 값은 기준 문서를 참조한다.
- 본문 없는 성공 응답에 빈 JSON이나 `data: null` 예시를 붙이지 않는다. 비동기 접수는 완료 결과와 구분하고 후속 확인 방법을 설명한다.

## 타입과 데이터 표현

- 언어의 클래스명보다 `String`, `Integer`, `Number`, `Boolean`, 객체와 배열 등 전송 형식을 기준으로 쓴다. 숫자는 필요한 범위와 형식을 덧붙인다.
- ID, 금액, 환율, 날짜와 시각은 Billit 공통 규칙의 전송 타입과 표현을 따른다. DB 컬럼 타입을 API 타입으로 그대로 옮기지 않는다.
- 금액과 환율은 통화와 단위, 날짜와 시각은 의미와 시간대가 필요한지 확인한다. 계산 방식이나 기간 경계가 미결이면 관련 정책의 결정을 연결한다.
- enum은 허용 값을 빠짐없이 적거나 해당 모델의 정의를 링크한다. 값의 의미는 용어집을 참조하고, 새 값을 작성하는 것과 도입을 결정하는 것을 구분한다.

## 오류와 처리 규칙

개별 API의 오류는 `HTTP`, `코드`, `조건` 열로 작성한다. 조건은 내부 예외 이름이 아니라 클라이언트가 오류를 받는 상황으로 설명한다. 오류 코드가 미결이면 임의로 확정하지 않는다.

도메인 오류 코드 사전은 문서 마지막에서 관리한다. 개별 API 표와 사전의 코드 및 HTTP 상태를 맞추고, 공통 오류의 형식과 메시지를 별도로 재정의하지 않는다.

멱등성, 동시 수정과 재요청을 다루는 API는 클라이언트가 지켜야 할 키의 범위, 요청 내용이 달라진 경우의 처리, 만료와 충돌, 재응답 규칙을 설명한다. 아직 정하지 않은 값과 동작은 남은 결정으로 표시한다. 내부 클래스, Repository와 쿼리 호출 순서는 설계서에서 다룬다.

## 예시 작성

- JSON 예시는 필드 표의 타입, 필수 여부와 포함 조건을 만족하는 완전한 JSON으로 작성한다. 생략 기호와 주석은 넣지 않는다.
- 일부 필드만 정해졌다면 그 범위를 표시하고 전체 요청이나 응답 예시는 보류한다. 알려지지 않은 필드를 추측해 완성하지 않는다.
- 예시에는 실제 개인정보, 운영 토큰과 내부 주소를 넣지 않는다. 설명용 식별자, 날짜와 금액은 서로 관계가 맞아야 한다.
- 성공 본문의 공통 감싸기 구조를 빠뜨리거나 ID와 금액을 저장 타입에 맞춰 숫자로 바꾸지 않는다. 제안 계약의 예시도 제안임을 표시한다.

## 완료 전 확인

- 목차, API 목록과 본문의 기능, 경로, 인증과 상태가 일치하는가?
- 확정 계약은 대응하는 OpenAPI와 연결되고, 변경 대상이 명확한가?
- 요청의 위치, 필수 여부, 기본값과 null 허용 여부를 구분했는가?
- 응답의 nullable과 포함 조건, 공통 구조와 모델이 일치하는가?
- 오류 조건과 코드 사전, 실제 계약 사이에 차이가 없는가?
- JSON 예시가 유효하고 필드 표를 만족하는가?
- 미결인 계약을 임의로 채우거나 정책과 설계를 중복 정의하지 않았는가?

문서 검사는 실제 HTTP 응답 검증을 대신하지 않는다. 구현과의 일치를 확인했다면 대상 커밋과 실행한 검증을 구분해 기록한다.
