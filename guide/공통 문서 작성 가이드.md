# 공통 문서 작성 가이드

## 목적과 적용 범위

이 가이드는 Billit 문서의 내용, 문체와 전개를 일관되게 유지하는 기준이다. 작성자나 사용하는 AI 도구와 관계없이 적용한다. 문서별 목차와 상세 형식은 유형별 가이드에서 정한다.

문서는 팀원이 현재 기준을 찾고, 조건에 따른 결과와 선택의 근거를 이해할 수 있도록 작성한다. 짧게 쓰는 것보다 정확하게 이해할 수 있게 쓰는 것을 우선한다.

## 문서별 역할

| 문서 | 관리하는 내용 |
| --- | --- |
| 정책서 | 권한, 허용과 제한, 계산 기준, 상태 전환과 운영 규칙 |
| API 스펙 | 클라이언트가 요청을 만들고 응답을 처리하는 데 필요한 계약과 검토안 |
| 용어집 | 기준 용어, 맥락별 표현, 사용하지 않는 용어, 유형값과 상태값의 의미 |
| 설계서 | 정책을 구현하는 테이블과 제약, 처리 순서, 트랜잭션과 실패 처리 |
| 문서 저장소 논의 Issue | 결정의 배경, 검토한 선택지와 이유 |
| 서버 저장소의 Issue와 PR | 구현 진행 상황과 검증 결과 |
| 서버 저장소의 `docs/` | 서버 설정, 배포와 운영 절차 |

같은 규칙을 여러 문서에서 독립적으로 정의하지 않는다. 다른 문서의 기준이 필요하면 해당 절을 링크하고, 현재 문서의 이해에 필요한 연결 설명만 작성한다.

화면 구성과 사용자 흐름은 Figma를 참조한다. 이 저장소에 별도의 화면 정의서를 작성하지 않는다. API Markdown은 검토와 설명을 위한 문서이며, 확정된 실행 가능한 계약은 백엔드 OpenAPI에서 관리한다.

## 근거와 확정 여부

### 근거 확인

- 작성 전에 문서의 독자, 목적, 다룰 범위와 근거 자료를 확인한다.
- 팀에서 확정한 결정과 정책, 확정 표시가 있는 Figma 화면, 기존 문서를 확인한다. 회의록과 대화에서는 제안과 최종 결론을 구분한다.
- 코드는 현재 구현을 확인하는 근거로 사용한다. 구현되어 있다는 이유로 확정 정책이라고 해석하지 않는다.
- 자료 사이에 충돌이 있으면 변경 경위와 적용 범위를 확인한다. 수정일이 최신이라는 이유만으로 우선하지 않는다. 판단할 근거가 부족하면 차이와 확인할 대상을 남긴다.
- 출처는 확인 가능한 문서나 절의 링크, Figma 화면 식별자, 논의 날짜, PR 또는 커밋으로 남긴다. 변경될 수 있는 외부 자료는 필요하면 버전이나 확인 기준일도 기록한다.
- 기존 문서에서 참조한 자료를 직접 확인하지 않았다면 확인한 것처럼 쓰지 않는다.

### 정책, 설계와 구현 상태

결정이 확정된 것과 구현이 끝난 것은 다르다. 정책 확정을 구현 완료로 표현하거나, 설계 제안을 적용된 구조처럼 설명하지 않는다.

정책서, API 스펙, 용어집과 설계서에는 구현 진행 상황을 쓰지 않는다. 구현 여부와 배포 여부는 서버 저장소의 Issue와 PR에서 확인한다. 코드 검토, 테스트 실행과 배포 확인은 서로 다른 근거로 구분한다.

### 미결정 사항

문서 본문에는 확정한 내용만 쓴다.
정하지 않은 내용은 문서에 쓰지 않고 이 저장소의 논의 Issue로 관리한다.
논의 Issue는 [문서 기여 규칙](../CONTRIBUTING.md#issue)에 따라 Billit 프로젝트의 DOCS 보기에 다음 Status로 등록한다.

| Status | 기준 |
| --- | --- |
| 지금 당장 해결해야 하는 문제 | 1차 MVP의 구현, 화면과 API 계약을 정하는 데 필요한 결정 |
| 나중에 해결해야 하는 문제 | 1차 MVP 이후나 운영 단계에서 정해도 되는 결정, 반영하기로 정했지만 현재 범위에 넣지 않은 내용 |

- 문서에는 `논의 필요`, `추후 반영`, `추후 검토` 같은 상태 표시를 쓰지 않는다. `제안`, `후보`, `검토안`, `미정`처럼 확정하지 않았음을 알리는 표현도 쓰지 않는다.
- 미결 내용 대신 다른 문서의 미결 사항을 따른다는 문장이나 논의 Issue 링크를 남기지 않는다.
- 일부만 정한 영역은 확정한 범위만 본문에 쓴다. 남은 선택을 본문에서 정한 것처럼 쓰지 않는다.
- 둘지 정하지 않은 기능, API와 모델은 정할 때까지 문서에 쓰지 않는다. 초안은 논의 Issue에서 다룬다.
- 결정하면 정한 기준을 본문에 쓴다. 결정의 이유는 논의 Issue의 `논의 결과`나 결정 근거를 남긴 PR을 링크한다.

## 문체와 문장

### 기본 문체

자연스러운 한국어 문장, 주체와 대상의 표현, 번역투와 문장부호 기준은 [한국어 표현 가이드](<한국어 표현 가이드.md>)를 따른다.

- 설명은 한다체로 작성한다. 문장과 명사형 종결의 위치는 [한국어 어미 가이드](<한국어 어미 가이드.md>)를 따른다.
- 한 문장에는 하나의 중심 판단을 담는다. 조건과 결과처럼 함께 읽어야 하는 내용은 한 문장으로 연결할 수 있다.
- 작성자 개인의 감상, 독자에게 말을 거는 표현과 대화에서만 필요한 해명을 넣지 않는다.

### 판단할 수 있는 표현

`할 수 있다`, `해야 한다`, `한다`, `하지 않는다`는 구분한다. 허용 여부, 의무와 확정된 동작을 문체 통일을 이유로 서로 바꾸지 않는다. 의무 수준별 표현은 [요구사항 문장 가이드](<요구사항 문장 가이드.md#의무-수준>)를 따른다.

## 문단과 설명 흐름

각 절은 독자가 알아야 할 규칙이나 결론으로 시작한다. 배경은 그 규칙을 이해하거나 선택을 판단하는 데 필요한 만큼 설명한다. 문서 전체에 같은 전개 순서를 기계적으로 적용하지는 않는다.

- 정책은 핵심 규칙을 먼저 쓰고 적용 조건, 예외와 필요한 예시를 이어 쓴다. 개별 규칙에서는 조건을 먼저 제시하고 결과를 명확히 쓴다.
- 설계는 채택한 방식과 보장할 동작을 먼저 쓰고, 저장 구조와 처리 흐름, 실패 결과와 선택 근거를 설명한다. 채택하지 않은 안은 제안으로 구분한다.
- API 설명은 기능과 사용 조건을 먼저 밝히고, 요청과 응답을 이해하는 데 필요한 계약을 설명한다. 업무 규칙 전체를 다시 옮기지 않는다.
- 한 문단에는 하나의 중심 내용을 둔다. 같은 규칙을 요약, 본문과 주의사항에서 표현만 바꿔 반복하지 않는다.
- 앞 문장의 대상을 이어 설명할 때는 관계가 드러나게 쓴다. 지시 대상이 모호한 `이것`, `해당 처리`, `이러한 방식` 대신 필요한 대상을 명시한다.
- 문장을 무조건 짧게 나누거나 접속사를 붙여 연결하지 않는다. 조건과 결과, 원인과 영향, 순서를 독자가 추측하지 않도록 연결한다.

예를 들어 [지출 생성 멱등성](../design/expense.md#지출-생성-멱등성)은 다음 순서로 설명할 수 있다.

> 앱은 지출 저장 요청에 고유키를 함께 보낸다. 서버는 같은 키의 재요청으로 지출을 다시 저장하지 않는다.
>
> DB에 지출을 저장했지만 앱이 응답을 받지 못한 경우에도 같은 키로 재시도한다. 서버는 이미 처리한 요청임을 식별해 지출이 두 건 생기지 않도록 한다.

확정된 보장과 그 보장이 필요한 상황을 쓴다.
남은 결정은 [미결정 사항](#미결정-사항)에 따라 논의 Issue로 관리하고, 설명 순서를 다듬는 과정에서 그 결론을 대신 정하지 않는다.

## 용어와 표기

- 같은 개념에는 같은 용어를 쓴다. 반복을 피하려고 동의어를 번갈아 사용하지 않는다. 용어집이 있으면 기준 용어를 따른다.
- 낯선 약어와 기술 용어는 처음 등장할 때 필요한 의미를 설명한다. 독자가 이미 아는 개념까지 매번 풀어 쓰지는 않는다.
- 화면에 그대로 표시하는 문구는 백틱으로 감싸고 원문을 유지한다. 화면 식별자, 상태값, API 경로, 파일명과 설정값도 백틱으로 표시한다.
- 클래스명, 내부 함수명과 라이브러리 이름은 문서의 판단과 구현 이해에 필요한 경우에만 쓴다.
- 날짜는 `YYYY-MM-DD`로 작성하고 기간과 수량에는 단위를 쓴다. 시각은 시간대에 따라 의미가 달라지는 경우 시간대도 밝힌다.

## 정보 표현

- 짧은 문단과 1단계 목록을 기본으로 사용한다. 순서가 중요한 절차에만 번호를 붙인다.
- 문단 안에서는 한 문장을 한 줄로 작성한다. 렌더링 결과는 같고, 여러 팀원이 같은 문단의 다른 문장을 수정할 때 충돌이 줄어든다. 기존 문서를 이 형식으로 일괄 변경하지 않고, 수정하는 문단부터 적용한다.
- 같은 기준으로 조건별 결과나 여러 대상을 비교할 때 표를 사용한다. 긴 설명을 표 안에 넣어 읽기 어렵게 만들지 않는다.
- 예시는 복잡한 규칙이나 실패 상황을 이해하는 데 필요할 때 둔다. 입력과 조건, 행동, 결과를 보여주고 설명용 값과 미결 조건에 대한 가정을 구분한다. 예시 블록의 종류와 형식은 [예시 블록 가이드](<예시 블록 가이드.md>)를 따른다.
- 코드와 SQL, JSON 예시는 본문과 같은 조건을 따른다. 예시에만 새로운 필드, 정책이나 예외를 추가하지 않는다.
- 내부 참조는 상대 링크로 작성한다. 다른 저장소의 자료는 팀원이 접근할 수 있는 저장소 링크를 사용하고, 개인 컴퓨터의 경로에 의존하지 않는다.

## 기존 문서 수정

1. 전체 목차와 도입, 결론을 확인하고 수정할 절의 앞뒤와 관련 문서를 읽는다. 짧은 문서는 전체를 읽는다.
2. 해결할 문제와 필요한 변경을 구분한다. 내용을 덧붙이기 전에 기존 문장의 유지, 삭제, 통합이나 이동으로 해결할 수 있는지 확인한다.
3. 문서의 목적과 기존 흐름에 맞게 반영한다. 질문과 답변을 그대로 덧붙이거나 다른 절의 규칙을 복제하지 않는다.
4. 문체만 고칠 때는 조건, 수치, 예외, 적용 범위와 확정 여부를 보존한다. 의미가 모호하면 임의로 명확하게 만들어 쓰지 않고 확인할 사항을 남긴다.
5. 수정한 내용을 앞뒤 흐름과 관련 문서에 다시 대입한다. 중복, 모순과 더 이상 유효하지 않은 설명을 제거한다.

## 완료 전 확인

- 독자가 이 문서에서 확인해야 할 기준과 범위가 분명한가?
- 근거 없이 정책이나 설계를 추가하지 않았는가?
- 확정된 내용, 제안과 구현 상태를 구분했는가?
- 주체와 대상, 조건과 결과를 추측 없이 이해할 수 있는가?
- 각 절과 문단이 핵심을 먼저 전달하고 필요한 맥락을 이어 설명하는가?
- 문체를 다듬으면서 의무 수준, 수치나 예외를 바꾸지 않았는가?
- 같은 규칙을 반복하거나 같은 개념을 다른 용어로 표현하지 않았는가?
- 예시와 표, 코드가 본문과 일치하고 링크가 유효한가?
- 수정한 내용이 기존 문서와 관련 문서의 흐름에 자연스럽게 이어지는가?
