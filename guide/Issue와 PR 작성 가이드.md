# Issue와 PR 작성 가이드

## 목적과 적용 범위

이 가이드는 Billit 문서 저장소와 서버 저장소의 Issue, PR과 코멘트를 쓰는 기준이다. 저장소의 Issue 템플릿과 PR 템플릿은 이 가이드의 섹션을 따른다. 문장은 [한국어 표현 가이드](<한국어 표현 가이드.md>)를 따르고, 기본 어미는 합니다체다.

브랜치, 라벨, 담당자, 리뷰와 병합 절차는 저장소마다 다르므로 다음 문서에서 정한다.

| 저장소 | 절차 문서 |
| --- | --- |
| 문서 저장소 | [문서 기여 규칙](../CONTRIBUTING.md) |
| 서버 저장소 | [Git 작업 규칙](https://github.com/JECT-Study/Billit-5th-Server/blob/develop/docs/contributing/git-workflow.md) |

## 공통 규칙

- Issue와 PR을 읽는 팀원은 작성 과정의 대화를 보지 않았다고 보고 쓴다. 회의와 대화의 경과는 쓰지 않고 결론과 출처만 쓴다.
- 기존 정책서, API 스펙, 설계서와 Issue에 있는 내용은 다시 쓰지 않고 링크한다.
- 섹션 제목은 `##`로 쓰고 이모지와 구분선을 쓰지 않는다.
- 내용이 없는 섹션은 지우지 않고 `없음`과 이유 한 문장을 쓴다. PR의 `변경 예시`와 `세부 사항`은 예외로, 내용이 없으면 섹션을 지운다.
- 저장소 템플릿은 이 가이드의 섹션 뒤에 브랜치와 리뷰어 지정 같은 절차 확인 목록을 둘 수 있다.
- 답이나 행동이 필요한 사람만 멘션한다. 멘션은 요청 문장의 첫머리에 쓴다.
- AI 도구의 이름이나 생성 표기를 쓰지 않는다.

## 단위 기준

### Issue 단위

- 작업 Issue 하나는 한 사람이 한 저장소에서 끝내고, 그 저장소 안에서 완료 조건을 확인하는 범위로 만든다.
- 서버 저장소의 작업 Issue는 API 스펙의 API 하나나 설계서의 `##` 절 하나를 단위로 만든다. API 여러 개가 같은 테이블 변경이나 같은 트랜잭션을 함께 쓰면 하나의 Issue로 만든다.
- 완료 조건이 8개를 넘거나 예상 작업 기간이 3일을 넘으면 Issue를 나눈다.
- 완료 조건이 1개이고 다른 열린 Issue와 같은 API나 문서를 바꾸면 그 Issue에 합친다.
- 버그 Issue 하나에는 재현 방법이 같은 현상 하나를 쓴다.
- 논의 Issue 하나에는 결정 하나를 쓴다. 서로의 결과에 영향을 주는 결정만 한 Issue의 `결정할 내용`에 번호를 붙여 함께 쓴다.
- 동시에 나누어 작업하거나 따로 완료하는 범위만 하위 Issue로 만든다. 하위 Issue의 `참고 자료`에는 상위 Issue를 쓴다.
- 기능 하나가 문서 저장소와 서버 저장소에 걸치면 저장소마다 Issue를 만든다. 각 Issue의 `참고 자료`에 다른 저장소의 Issue를 쓴다.

### PR 단위

- PR 하나에는 리뷰어에게 요청하는 판단 하나를 담는다. 이 판단을 `변경 요약`의 마지막 문장에 쓴다.
- 서버 저장소의 PR은 테스트 코드, 생성된 코드와 lock 파일을 뺀 변경을 400줄 이하로 만든다. 400줄을 넘으면 선행 PR 위에 다음 PR을 쌓아 나눈다.
- 문서 저장소의 PR은 [문서 기여 규칙](../CONTRIBUTING.md#작업-분담과-충돌-방지)에 따라 업무 하나의 정책서, API 스펙과 설계서 변경을 함께 담는다.
- Issue 하나를 PR 여러 개로 나눌 수 있다. PR 하나로 Issue 여러 개를 닫지 않는다.
- 기능 변경, 리팩터링, 대규모 포맷 변경과 의존성 갱신은 서로 다른 PR로 만든다.

## 제목

- 작업 Issue, 버그 Issue와 PR의 제목은 `<type>: <대상과 바꿀 내용>` 형식으로 쓴다. `type`은 저장소의 커밋 type을 쓴다.
- 논의 Issue의 제목은 type 없이 `<대상>의 <정할 내용> 결정` 명사구로 쓴다.
- 제목은 50자 이하로 쓰고 끝에 마침표를 찍지 않는다.
- 변경 방법이 아니라 변경 대상과 결과를 쓴다.
- PR을 Squash merge하면 PR 제목이 커밋 제목이 된다. PR 제목은 저장소의 커밋 제목 규칙을 따른다.

다음은 가상 예시다.

```text
feat: 초대 코드로 여행 참여
fix: 만료된 토큰의 오류 응답 코드
docs: 여행 확정과 동시 인원 변경 처리 반영
여행 확정 중 동시 인원 변경 요청의 처리 방식 결정
```

## Issue 섹션

Issue의 `<details>` 밖의 본문은 코드 블록, 표와 링크 목록을 빼고 1,000자 이하로 쓴다. 1,000자를 넘으면 세부 근거를 `<details>`로 접는다.

### 작업 Issue

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 작업 배경 | 작업이 필요한 이유 | 문단, 3문장 이하 |
| 작업 범위 | 포함하는 일과 제외하는 일 | 문단과 보충 목록 |
| 완료 조건 | 완료를 판단하는 동작과 결과 | [요구사항 문장](<요구사항 문장 가이드.md>)의 체크박스 문장 목록 |
| 참고 자료 | 정책서, API 스펙, 설계서, 화면 식별자, 관련 Issue | 링크 목록 |

- 구현 방식은 작업 범위나 판단에 영향을 줄 때만 `작업 범위`에 쓴다.
- 완료 조건에는 `기능 구현 완료`, `테스트 완료`처럼 통과와 실패를 가를 수 없는 항목을 쓰지 않는다.
- 배포나 통합 환경에서만 확인할 수 있는 동작도 완료 조건에 쓴다.

### 버그 Issue

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 현상 | 사용자나 시스템이 겪는 문제 | 문단, 2문장 이하 |
| 재현 방법 | 문제를 다시 일으키는 단계 | 번호 문장 목록 |
| 기대 동작과 실제 동작 | 같은 입력의 기대 결과와 실제 결과 | 변경형 예시 블록. `# As-is`에 실제 동작, `# To-be`에 기대 동작 |
| 발생 환경 | 앱 버전, 운영체제, 서버 환경, 브랜치 | 보충 목록 |
| 스크린샷과 로그 | 문제를 확인하는 자료 | 첨부 |

- 재현 조건을 확인하지 못했으면 `재현 방법`에 `재현 조건을 확인하지 못했습니다.`와 확인한 발생 상황을 쓴다.
- 스크린샷과 로그에서 개인정보, 토큰과 비밀값을 지운다.

### 논의 Issue

논의 Issue는 문서 저장소에 만든다. 설계서와 정책서가 결정의 근거로 링크하는 곳을 한 저장소로 모으기 위해서다.

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 배경 | 현재 기준과 결정이 필요한 이유 | 문단, 4문장 이하 |
| 결정할 내용 | 정할 질문과 선택지 | 번호 문장 목록과 하위 보충 목록 |
| 확인 요청 | 의견이나 결정이 필요한 팀원 | 멘션으로 시작하는 문장 목록 |
| 참고 자료 | 대상 문서의 절, 회의록 이름, 관련 PR | 링크 목록 |
| 논의 결과 | 결정, 이유, 검토한 선택지, 영향 범위, 문서 반영 | 논의를 마친 뒤 [논의 결과 형식](#논의-결과-형식)으로 씀 |

- 결정할 내용의 항목은 `<대상>을 <무엇>으로 할지 정합니다.`로 쓴다.
- 선택지는 하위 보충 목록에 `<선택지>: <결과>` 명사형으로 쓴다.

### 논의 결과 형식

논의 Issue의 `논의 결과`는 팀의 결정 기록이다. 설계서와 정책서는 결정의 이유를 쓰지 않고 이 기록을 링크하므로, 논의를 마치면 다음 형식으로 쓴다. 다음은 가상 예시다.

```markdown
## 논의 결과

- 결정: 지출 수정 잠금은 Redis 대신 DB 행 잠금을 씁니다.
- 이유: 잠금과 지출 수정을 한 트랜잭션에서 처리해 잠금만 남는 경우를 없앱니다.
- 검토한 선택지:
  - Redis 분산 잠금: 트랜잭션이 실패하면 잠금을 따로 풀어야 함
  - 낙관적 잠금: 동시 수정이 잦은 정산 준비에서 재시도가 많음
- 영향 범위: 지출 수정 API, 정산 준비 API
- 문서 반영: #45
```

- 필드는 `결정`, `이유`, `검토한 선택지`, `영향 범위`, `문서 반영` 순서로 쓰고 빼지 않는다.
- `결정`과 `이유`는 합니다체 문장으로 쓴다. 나머지 필드는 명사형으로 쓴다.
- `결정할 내용`이 둘 이상이면 번호마다 `논의 결과`의 형식을 반복한다.
- 결정을 보류하거나 제안을 채택하지 않으면 `결정`에 `보류합니다.`나 `채택하지 않습니다.`를 쓰고 `이유`를 쓴다.
- 문서에 반영하지 않으면 `문서 반영`에 `없음`과 이유를 쓴다. 문서를 반영하는 PR이 병합되면 `문서 반영`에 그 PR을 쓴다.
- 결정이 바뀌면 기존 `논의 결과`를 고치지 않는다. 새 논의 Issue를 만들고, 기존 Issue에 새 Issue 링크를 코멘트로 남긴다.

## PR 섹션

| 섹션 | 내용 | 형태 |
| --- | --- | --- |
| 관련 Issue | 완료하는 Issue와 관련 Issue | `Closes #번호`, `Related #번호` |
| 변경 요약 | 무엇을 왜 바꿨는지와 리뷰어가 판단할 내용 | 문단, 3문장 이하 |
| 변경 예시 | 바뀐 동작이나 기준 | [변경형 예시 블록](<예시 블록 가이드.md#변경형>) |
| 리뷰 포인트 | 리뷰어의 판단이 필요한 결정, 호환성, 배포 순서, 다른 문서와 구현에 주는 영향 | 문장 목록 |
| 검증 결과 | 실행한 검증과 결과, 실행하지 못한 검증과 이유 | 도입 문장과 보충 목록 |
| 세부 사항 | 변경 위치, 대안 비교, 긴 근거 | `<details>` |

- `변경 요약`의 마지막 문장은 리뷰어에게 판단을 요청하는 `-해 주세요` 문장으로 쓴다.
- 문서 저장소의 PR은 `변경 요약`의 첫 문장에 확정한 결정을 반영하는지, 새 기준을 제안하는지 쓴다.
- 동작이나 기준이 바뀌지 않으면 `변경 예시` 섹션을 지운다.
- `리뷰 포인트`에는 구현 설명을 반복하지 않는다. 가이드를 따르지 않았으면 이유를 쓴다.
- `검증 결과`는 검사 이름과 결과를 명사형으로 쓴다. 재현에 필요하지 않으면 전체 명령, 실행 환경과 로그를 쓰지 않는다.
- 실행하지 못한 검증은 `-하지 못했습니다` 문장과 이유로 쓴다.
- 문서 링크 검사나 SQL 조건의 정적 확인을 실제 DB 동작이나 동시성 검증으로 쓰지 않는다.

### PR 분량

- `<details>` 밖의 본문은 코드 블록을 빼고 800자 이하로 쓴다.
- 800자를 넘으면 세부 근거와 변경 위치를 `<details>`로 접는다.
- 오탈자, 서식과 이름만 바꾸는 PR은 `변경 요약`만 한 문장으로 쓴다. `변경 예시`와 `세부 사항`은 지우고, 나머지 섹션 중 내용이 없는 섹션에는 `없음`과 이유를 쓴다.

## 코멘트

Issue와 PR의 코멘트, 코드 리뷰 코멘트에 적용한다.

- 첫 문장에 결론이나 요청을 쓴다.
- 인사와 감사 문장을 쓰지 않는다.
- 코멘트 하나에는 주제 하나를 쓴다.
- 코드 블록과 인용을 뺀 본문은 5문장 이하로 쓴다. 더 길면 Issue나 문서에 쓰고 링크한다.
- 스레드에 이미 있는 내용을 다시 쓰지 않는다.

### 리뷰 코멘트

리뷰 코멘트의 첫머리에는 다음 표의 표지 하나를 쓴다.

| 표지 | 뜻 | 작성자의 행동 |
| --- | --- | --- |
| `필수:` | 병합 전에 고쳐야 하는 문제 | 고치고 답글로 알림 |
| `제안:` | 더 나은 방법의 제안 | 반영 여부를 정하고 답글로 알림 |
| `질문:` | 판단에 필요한 정보의 요청 | 답글로 답함 |

- 표지 다음 문장에 문제나 요청을 쓰고, 그다음 문장에 근거를 쓴다.
- 코드를 고쳐야 하면 GitHub의 `suggestion` 블록으로 고친 코드를 보여 준다.
- `필수:` 코멘트의 근거에는 깨지는 동작이나 어긋나는 규칙을 쓴다.

```markdown
필수: 서버가 확정된 여행의 참여 요청도 저장합니다. 정책서의 `확정 이후` 규칙은 확정된 여행에 참여할 수 없다고 정합니다.
```

### 답글

- 질문에 대한 답을 첫 문장에 쓴다.
- 코멘트를 반영했으면 `반영했습니다.`와 커밋 링크를 쓴다.
- 반영하지 않으면 `반영하지 않습니다.`와 이유 한 문장을 쓴다.

### 진행 상황 코멘트

- 작업 하나의 진행 상황은 코멘트 하나에 쓰고, 상황이 바뀌면 그 코멘트를 수정한다.
- 진행 상황은 `완료`, `진행 중`, `막힘` 항목의 보충 목록으로 쓴다.

```markdown
작업 상황을 다음과 같이 공유합니다.

- 완료: 초대 코드 검색 API를 연결함
- 진행 중: 참여 요청 화면을 만듦
- 막힘: 정원 초과 응답 코드를 정하지 않음 (#34)
```

## 쓰지 않는 내용

다음 내용은 Issue, PR과 코멘트에 쓰지 않는다.

- 작성 과정의 대화를 가리키는 표현
- worktree 이동, 임시 브랜치처럼 작성자의 내부 작업 과정
- diff에서 확인하는 파일 목록, 코드와 구현 순서
- 같은 내용의 반복

## 작성 예시

다음은 가상 예시다.

### 작업 Issue

```markdown
## 작업 배경
```
