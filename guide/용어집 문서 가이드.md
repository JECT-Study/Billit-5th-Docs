# 용어집 문서 가이드

## 목적과 적용 범위

이 가이드는 팀이 공통으로 사용하는 용어와 상태의 의미를 정의하는 기준이다. 근거와 상태는 [공통 문서 작성 가이드](<공통 문서 작성 가이드.md>)를, 문장은 [한국어 표현 가이드](<한국어 표현 가이드.md>)를 따른다.

용어집은 같은 개념을 서로 다른 말로 부르거나, 같은 말을 다른 의미로 해석하는 문제를 줄이기 위해 작성한다. 업무 규칙과 처리 절차를 모아 놓는 문서로 사용하지 않는다.

## 관리 범위와 구조

용어집은 `glossary/glossary.md` 한 곳에서 관리하고 업무 영역별 절로 나눈다. 여러 영역이 공유하는 개념은 공통 영역에 한 번만 정의하고 필요한 곳에서 연결한다. 실제 용어집은 합의된 용어를 확인한 뒤 작성한다.

등록 대상은 다음과 같다.

- 팀이 공통으로 구분해야 하는 업무 개념과 기준 용어
- 사용자, 도메인과 화면에서 같은 개념을 다르게 표현하는 경우의 대응 관계
- 혼동을 막기 위해 사용하지 않는 표현
- 업무상 구분이 필요한 유형값과 상태값의 의미

일상적인 단어, 특정 화면에만 있는 안내 문구와 내부 클래스명은 등록하지 않는다. API 필드 목록과 DB 컬럼 목록을 그대로 옮기지 않는다.

## 기준 용어 표

```markdown
## [업무 영역]

| 기준 용어 | 정의 | 사용자 용어 | 도메인 용어 | 화면 용어 | 사용하지 않는 용어 |
| --- | --- | --- | --- | --- | --- |
| [용어] | [다른 개념과 구분되는 의미] | [다른 표현 또는 -] | [다른 표현 또는 -] | [표시 표현 또는 -] | [혼동을 일으키는 표현 또는 -] |
```

- 하나의 개념에는 하나의 기준 용어를 둔다. 문서와 회의에서는 기준 용어를 사용한다.
- 정의에는 해당 개념을 다른 개념과 구분하는 의미를 쓴다. 정의하려는 용어를 반복하는 순환 설명은 피한다.
- 역할이 겹칠 수 있어도 의미가 다르면 구분한다. 예를 들어 결제한 사람과 지출을 기록한 사람을 같은 개념으로 정의하지 않는다.
- 맥락별 표현이 기준 용어와 같으면 `-`로 표시한다. 이 표의 맥락별 표현 열에서 `-`는 별도의 표현 차이가 없다는 뜻이다.
- 표현이 필요한데 아직 정하지 않았다면 `-`로 숨기지 않는다. 그 칸을 비워 두고 [미결정 사항](<공통 문서 작성 가이드.md#미결정-사항>)에 따라 논의 Issue로 관리한다.
- 화면이나 상황별로 문구가 다르면 대표 문구를 임의로 고르지 않는다. 해당 칸에 관련 Figma 화면의 이름이나 식별자와 링크를 작성한다.
- 사용하지 않는 용어가 여러 개면 쉼표로 구분한다. 사용을 피하는 이유나 적용 범위는 표 아래에서 설명한다. 서로 다른 개념을 단순한 동의어로 묶지 않는다.

도메인 용어는 업무 모델에서 사용하는 개념의 이름을 뜻한다. 현재 클래스명이나 테이블명과 기계적으로 맞추지 않으며, API 필드명은 계약 문서에서 관리한다.

## 유형값과 상태값

업무 영역에서 유형이나 상태를 구분한다면 기준 용어 표 다음에 값의 의미를 작성한다.

```markdown
### 유형값과 상태값

| 구분 | 영문 식별자 | 한글 값 | 영문 값 | 화면 표시값 | 의미 |
| --- | --- | --- | --- | --- | --- |
| [유형 또는 상태] | `[식별자]` | [한글 이름] | `[VALUE]` | [표시값 또는 Figma 링크] | [다른 값과 구분되는 의미] |
```

- 영문 식별자는 어떤 유형이나 상태의 값 집합인지, 영문 값은 그 집합의 개별 값을 뜻한다. 실제 계약이나 모델에 정의된 경우에만 기록한다.
- 영문 이름과 코드가 미결이면 한글 개념 정의만 쓰고, 영문 이름과 코드는 논의 Issue로 관리한다. 번역이나 대문자 변환으로 코드를 새로 확정하지 않는다.
- 같은 개념의 구현별 코드가 다르면 대응하는 계약이나 설계를 링크한다. 서로 다른 코드 체계를 하나의 값처럼 합치지 않는다.
- 화면 표시값은 원문을 유지한다. 화면이나 언어별로 다르면 관련 Figma 화면을 연결한다. 확인하지 않은 번역을 만들지 않는다.
- 값의 의미에는 다른 값과 구분되는 상태나 조건을 설명한다. 상태 전환 권한, 처리 순서와 예외는 정책서를 링크한다.
- 추가 후보와 폐기된 값은 현재 사용 중인 값과 구분한다. 현재 허용 값 목록은 API 계약과 일치하는지 확인한다.

## 관련 문서와 변경

권한, 검증, 계산, 상태 전환과 처리 규칙은 용어집에 재정의하지 않는다. 필요한 정책과 설계의 해당 절을 링크한다. 용어집에서 단어를 바꾸는 것으로 업무 정책이나 API 값을 변경하지 않는다.

용어의 의미나 기준 표현을 바꾸면 관련 정책, API 스펙과 설계의 사용처를 확인한다. API 필드명이나 enum 값까지 바뀌는 경우에는 별도 계약 변경으로 다루고 관련 PR을 연결한다. 과거 기록의 원문까지 일괄 치환하지 않는다.

## 완료 전 확인

- 기존 용어와 같은 개념을 중복 등록하지 않았는가?
- 기준 용어의 정의만으로 다른 개념과 구분할 수 있는가?
- 맥락별 표현과 사용하지 않는 표현이 올바른 개념에 연결되는가?
- 미결인 표현을 `-`로 숨기지 않고 논의 Issue로 옮겼는가?
- 유형값과 상태값의 코드가 실제 계약이나 모델과 일치하는가?
- 정의에 정책이나 구현 절차를 중복해서 넣지 않았는가?
- 용어 변경이 영향을 주는 문서와 계약을 확인했는가?
