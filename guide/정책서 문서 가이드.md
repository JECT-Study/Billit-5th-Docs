# 정책서 문서 가이드

## 목적과 적용 범위

이 가이드는 `policy/`에 업무 정책을 작성하는 기준이다. 근거와 상태, 설명 흐름은 [공통 문서 작성 가이드](<공통 문서 작성 가이드.md>)를, 문장은 [한국어 표현 가이드](<한국어 표현 가이드.md>)를 따른다.

정책서는 화면, API와 구현이 따라야 하는 업무 조건과 결과를 정의한다. 구현되어 있다는 이유로 정책을 정당화하거나, 구현의 빈틈을 새로운 업무 규칙으로 채우지 않는다.

## 문서 구조

제목은 `[업무 영역] 정책서`로 작성한다. 제목 바로 아래에 목차를 두고, 본문은 업무 흐름에 맞춰 배치한다. 대분류는 화면, API나 클래스가 아니라 업무 영역을 기준으로 나눈다.

```markdown
# 환율 정책서

## 목차

- [개인 환율 기록](#개인-환율-기록)
- [지출 환율](#지출-환율)
- [저장된 지출과 정산](#저장된-지출과-정산)

## 개인 환율 기록

## 지출 환율

## 저장된 지출과 정산
```

별도의 목적 절로 제목과 내용을 반복하지 않는다. 적용 범위가 혼동될 수 있으면 관련 영역에서 대상과 제외 범위를 밝힌다. 목차에는 실제 업무 영역과 하위 항목을 연결한다.

각 영역은 다른 영역을 순서대로 읽지 않아도 필요한 정책을 찾을 수 있게 작성한다. 핵심 규칙을 먼저 쓰고 적용 조건과 예외, 필요한 예시를 이어 쓴다. 다른 영역의 기준이 필요하면 짧게 연결하고 해당 절을 링크한다.

## 정책에 포함할 내용

- 누가 어떤 대상에 대해 행동할 수 있는지 작성한다. 역할, 소유자와 실제 행위자가 다르면 구분한다.
- 허용과 제한의 조건, 처리 결과와 예외를 작성한다. 적용되는 대상, 시점과 범위가 드러나야 한다.
- 상태 전환은 시작 상태, 행동이나 조건, 결과 상태를 설명한다. 상태 이름만 나열하거나 화면의 버튼 이름으로 대신하지 않는다.
- 수치와 기간은 단위, 범위의 포함 여부와 필요한 기준 시점을 명확히 한다. 정해지지 않은 상한과 기간을 임의로 넣지 않는다.
- 업무 용어를 사용하고, API 필드명과 enum 코드가 없어도 정책을 이해할 수 있게 쓴다.

API의 경로, 요청과 응답 필드, HTTP 상태와 오류 코드는 API 스펙에서 관리한다. 테이블과 컬럼, 토큰 형식, Redis 키, 잠금과 트랜잭션 등 구현 선택은 설계서에서 관리한다. 보안과 개인정보도 사용자의 권리와 서비스의 제한은 정책에, 검증 프로토콜과 저장 방식은 관련 기술 문서에 작성한다.

## 조건과 결과 표현

개별 규칙은 조건을 먼저 제시하고 결과를 서술한다. 조건을 축약한 메모만 남기거나 원문에 없는 보장을 덧붙이지 않는다.

> 개인 환율을 등록하거나 변경해도 기존 지출의 환율과 부담액을 자동 변경하지 않는다.

위 예시처럼 적용 대상과 바뀌지 않는 범위를 함께 설명한다. `기존 지출은 유지한다`처럼 무엇을 유지하는지 알 수 없는 문장으로 줄이지 않는다.

여러 조건과 결과를 비교해야 하면 의사결정표를 사용한다. 표의 열은 판단에 필요한 조건과 결과로 구성하고, 모든 조합을 다루지 않으면 다루는 범위를 밝힌다. 예외가 있으면 표 아래에 설명한다.

## 권한 표현

한 기능의 권한은 조건과 결과를 문장으로 설명한다. 여러 기능과 역할을 비교할 때는 관련 영역 앞부분에 권한 표를 둔다.

기본 허용 여부가 확정된 경우에만 표에서 `허용`과 `불가`를 사용한다. 소유자, 여행 상태나 작업 시작 여부에 따라 달라지는 조건은 표 아래에서 기능별로 설명한다. 기본 권한을 정할 수 없을 정도로 조건이 다르면 조건을 별도 열이나 절로 나눈다.

표에 넣기 위해 역할이나 권한을 새로 만들지 않는다. 실제 결제자, 기록자와 여행 관리자처럼 다른 개념을 같은 역할로 취급하지 않는다.

## 적용 예시

복잡하거나 오해하기 쉬운 규칙에는 적용 예시를 둔다. `text` 코드 블록 안에서 사례에 번호를 붙이고, 조건과 행동 다음 줄에 결과를 작성한다. 사례 사이에는 빈 줄을 둔다.

다음은 [환율 정책](../policy/exchange-rate.md#저장된-지출과-정산)을 설명하는 예시다. 인물은 설명용이며 새 정책을 정의하지 않는다.

```text
1. 민지가 지출을 저장한 뒤 개인 환율을 변경한다.
   결과: 기존 지출에 저장한 환율과 부담액은 자동으로 바뀌지 않는다.

2. 변경한 개인 환율이 있어도 기존 지출을 정산한다.
   결과: 정산은 해당 지출에 저장된 환율을 사용한다.
```

예시는 확정된 규칙의 적용을 보여준다. 본문에 없는 예외, API 계약과 구현 방식을 추가하지 않는다. 미결인 정책에 따라 결과가 달라지면 가능한 결과와 남은 결정을 구분하고 하나를 정답으로 제시하지 않는다.

## 관련 화면과 근거

관련 절의 제목 아래에 `화면: `으로 시작하는 한 줄을 두고 Figma 화면 식별자를 백틱으로 표시한다. 여러 화면은 쉼표로 구분하고, 가능하면 해당 화면으로 이동하는 링크를 연결한다. 식별자가 없으면 Figma의 화면 이름과 링크를 사용한다.

화면은 정책의 근거와 이해를 돕는 자료이며 정책 본문을 대신하지 않는다. 업무 조건과 결과는 화면을 열지 않아도 이해할 수 있게 작성한다. 화면 구성과 안내 문구 전체를 정책서에 복제하지 않는다.

회의나 PM 답변으로 확정한 규칙은 필요한 위치에서 원문을 연결한다. `회의 결정`이라는 표시만으로 출처를 대신하지 않는다. 상태 표시는 공통 가이드를 따르며 정책서에서 별도 상태 체계를 만들지 않는다.

## 완료 전 확인

- 화면이나 구현 구조가 아니라 업무 영역을 기준으로 구성했는가?
- 주체, 대상, 조건과 결과, 예외와 적용 범위를 이해할 수 있는가?
- 권한 표와 본문이 같은 조건을 설명하는가?
- 적용 예시가 본문의 확정된 정책을 벗어나지 않는가?
- 관련 Figma 화면과 논의 근거를 찾을 수 있는가?
- API 계약이나 저장 구조를 정책으로 중복 정의하지 않았는가?
- 제안, 논의 필요와 확정된 내용을 구분했는가?
